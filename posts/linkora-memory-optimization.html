把常驻内存从 3.9GB 压到 0.5GB：三个「看不见」的内存大户

AI Agent 性能 内存 Python

活动监视器里那个后台进程吃掉了 3.9GB，可它跑的向量模型参数才 91MB。差了四十倍，显然有什么东西在偷偷占地方。查下来是两个谁都没注意到的隐性大户，一个来自 GPU，一个来自数据库，都挺反直觉。

先说个坑：ps 看到的内存是假的

一开始用 ps 查 RSS，这个进程只显示 126MB——跟 3.9GB 差了两个数量级。原因是 GPU 显存不计入 RSS，在 Apple Silicon 上统一内存架构下，Metal 分配的显存是进程真实占用的一部分，但 RSS 一行都体现不出来。

macOS 上要看真实占用，得用：

footprint -p <pid> -s

这一下就清楚了，3.9GB 里有 2250MB 是 IOAccelerator（GPU 显存），剩下的是一堆 Malloc。

大户一：MPS 后端固定白拿 1GB

项目用 PyTorch 的 MPS 后端在 Apple Silicon 上跑向量模型。做了组对照实验，结果挺意外：

  • 加载 91MB 参数的模型到 MPS，驱动显存直接跳到 1048MB；
  • 改成 fp16 直接加载（省一半权重），驱动显存 1040MB——几乎没变；
  • 调 torch.mps.empty_cache()，还是 1048MB，一点没回收；
  • 只有把模型对象 del 掉，才回落到 1MB。

也就是说：MPS 后端首次分配就向驱动申请了约 1GB 固定池，跟模型大小、精度都无关，而且释放不掉。对小模型来说，这 1GB 完全是净亏损。

那 GPU 到底带来了多少收益？实测 CPU 推理：单条短文本 15ms，384 token 长文本 20ms，32 条批量 0.46s。放在一个要跑网络请求、数据库查询、大模型调用的消息处理链路里，这几十毫秒根本感知不到。于是加了个 embedding.device 配置项，内存吃紧时设成 cpu，这块占用直接归零。

大户二：SQLite 页缓存会「越跑越高」

第二个更难发现，因为它只在跑久了之后才显现——正好对上「刚重启不高，跑一天就涨上去」的现象。

代码里为了规避 SQLite 的锁竞争，用了每个线程一个独立连接的方案，同时给每个连接设了 PRAGMA cache_size=-64000，也就是每连接 62.5MB 的页缓存上限。注意这是「每连接」，不是全局：进程有 37 个线程、实际开了 18 个连接，理论上限就奔着 GB 去了。

更要命的是页缓存是按查询量懒增长的，跑得越久、查得越多，就越接近上限。实测 9 个连接全表扫描 102MB 的会话库：

  • 62.5MB/连接 → RSS 513MB
  • 16MB/连接 → RSS 202MB
  • 8MB/连接 → RSS 115MB

降到 8MB 会不会拖慢查询？实测三档的查询耗时：按会话查最近 50 条（走索引）是 0.019s / 0.014s / 0.015s，全表扫描 11 万行是 0.150s / 0.145s / 0.149s——差异全在噪声里。原因也简单：真实查询走索引，热点数据只有几 MB；大范围扫描那 102MB 由系统文件缓存兜底，SQLite 自己多留缓存纯属重复劳动。最终定在 8MB。

大户三：重排模型偷偷选了 GPU

前两块改完，进程从 3.9GB 降到 0.6GB，本以为收工了。结果过一阵再看，又涨回 3.1GB。说明还有第三只手。

第三块是 rerank 重排模型（BAAI/bge-reranker-base），RAG 检索里的精排环节。它的加载代码是 CrossEncoder(model)，没指定 device——sentence_transformers 一看本机有 GPU，自动就选了 MPS。

最阴险的是它是 lazy-load（懒加载）：只在第一次真的触发 RAG 检索时才把模型塞进显存。于是表现成「刚重启不高、过一阵突然涨 1–2GB」，而且因为是按需才炸，footprint 采样十次有九次都抓不到。过程中 OCR 还背了锅，实测 RapidOCR / onnxruntime 在 CoreML 和 CPU 两档下 Metal 显存都是 0MB，已排除，别再往它身上查。

对着进程抓了现场：重排模型一旦加载，GPU 显存直接 +1094MB。实测对照：

  • 不指定 device（原行为）→ device=mps:0、驱动显存 1094MB；
  • 指定 device=cpu → 驱动显存 0MB，重排 5 组候选仅 0.05s（默认 rerank_timeout 是 2s，绰绰有余）。

改法跟第一块一致：让重排模型跟随同一个 embedding.device 开关。CPU 下毫无压力，显存白白省下 1GB。

结果

三块大头依次收掉：embedding 切 CPU 后进程从 3912MB 降到 563MB；再修掉重排模型自动选 GPU 那 1GB，进一步降到 486MB；Web 进程从 397MB 降到 144MB。合计降幅约 88%。向量维度始终是 512，知识库索引一行都没重建。

几条能直接抄走的经验

  • 排查内存先换工具：ps 的 RSS 在 macOS 上会严重低估，GPU 显存完全看不见，用 footprint -p <pid> -s。
  • 小模型别迷信 GPU：推理本身只占几十毫秒时，框架的固定开销（显存池、kernel 启动）往往远大于收益。先量，再决定要不要上加速后端。
  • 「每连接」「每线程」的配置要乘上并发数：单看 62.5MB 很合理，乘上 18 个连接就是另一个故事了。
  • 「跑得越久越占内存」优先查懒增长型缓存：不是泄漏，是缓存一路爬向上限。这类问题重启能缓解，但会原样复现。
  • 只在使用时才加载的模型，要盯着它的默认设备选择：lazy-load 的组件（重排、OCR、缓存预热等）往往图省事不传 device，框架就替你选了 GPU。这类「按需才炸」的涨内存最隐蔽——采样抓不到，得在它真正被触发之后再看 footprint。
